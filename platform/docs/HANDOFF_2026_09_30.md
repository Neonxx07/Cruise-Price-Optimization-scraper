## HARD RULES

- **No AI/LLM/API keys anywhere, ever.**
- **Never delete captured data** — `data/` is the corpus that improves results.
- **ESPRESSO never headless.** Re-tested three ways (anonymous, stale session,
  live warm session): headed 200, every headless mode 404 at the CDN edge.
- **Never deep-link into ESPRESSO's WebFlow from a freshly authenticated
  browser** — it resolves to the portal's own `&_eventId=logout`.
- **Never move `release_booking` out of `check_booking`'s `finally`.**
- **No `print()` on a GUI thread** — a paused Windows console blocks the
  writer and hangs the app.
- **A confirmed PAID_IN_FULL or CANCELLED booking is never rescanned.**
- **A positive `CRUISE_PROMO` is the PRICE OF A PERK — keep subtracting it.**

- Never log into ESPRESSO manually while a scan runs (one session per account).
- Passwords via `save_login.py` + OS keyring only, never in chat.

## WHAT WAS FIXED

### Scan awareness — don't rescan what the database already knows

**Measured: 565 of 1,393 rows in 24h (41%) were redundant, ~148 minutes.** Of
55 repeats where the total could be compared, **55 identical, 0 changed.**

The old cache had one writer (`set_no_saving`) gated on `status == NO_SAVING`,
so every other outcome was re-scanned every run — PAID_IN_FULL alone was 439
of the repeats. It stored only a timestamp, leaving `value_json` unused, so
skipped rows showed "1.4h ago" with every price column blank.

- **Per-line windows** — `settings.freshness_hours` (ESPRESSO 12h, NCL 6h,
  GoCCL 24h, MSC 12h), default `cache_ttl_hours`.
- **Every cacheable outcome** cached. `never_cache_statuses` keeps
  OPTIMIZATION, ERROR, CANCELLED, UNKNOWN out — a live saving must always be
  re-confirmed, a failure is not an outcome.
- **Bulk lookup** (`get_many`) — was 723 round trips before the first page.
- **Figures travel with the entry**, so a skipped row displays like a scanned one.

### Permanent exclusions — PAID_IN_FULL and CANCELLED

`services/exclusion_service.py` + `permanent_exclusions` table. Checked
**before the TTL cache and before any browser action**; not bypassable by
"Force live recheck".

`record_paid_in_full` refuses unless the payment panel was actually **read**,
a real `final_payment_due` exists, and `total_price > 0`. "Couldn't see the
balance" must never become "owes nothing" — that produced a false $400 on
booking 3001001, which had two cents outstanding.

Cancellations are still **REPORTED every run** (mandatory) — they come back
as CANCELLED from the register instead of the portal. Only the scraping stops.

Every entry stores evidence; `clear()` lifts one while keeping the row.

### Price-change detection

`core/price_change.py` — drop / increase / unchanged against the previous
`price_history` row, with a £1 noise floor. A drop is surfaced on the row.
6,606 history rows existed and nothing had ever compared two of them.

### Session recovery: one-shot → rate-limited

ESPRESSO drops a session roughly **hourly**; the old "one recovery per batch"
guaranteed every long scan died partway (399 unchecked on 09-29). Now a rate
limit: recover freely when logouts are far apart, stop only when back-to-back
(`_RECOVERY_MIN_GAP_S=180`, `_RECOVERY_MIN_BOOKINGS=3`, `_RECOVERY_MAX=12`).
**The interrupted booking is now retried**, not silently dropped — `continue`
had been jumping over `job.results.append()`, so it got no row at all.

### auto_login falsely reporting ALREADY_LOGGED_IN

It asked "am I logged in?" **2 seconds after browser start**, while a dead
restored session was still redirecting to `/login`, and returned
ALREADY_LOGGED_IN **without ever filling the credential**. Fixed by settling
first. Verified live: `auto_login_form_found` → `result=OK` → `via=auto_login`.

### Start now logs you in

Pressing Start on a fresh app refused and told you to press "Check login" —
while the credentials sat in the keyring and auto_login took nine seconds.
Start now attempts the login itself; the logged-out guard remains as the
**second** answer if that fails (ESPRESSO can demand MFA).

### GUI heaviness — 352.8ms → 0.002ms

`_update_queue_view` built a `QWidget + layout + label + button` per row and
rebuilt the whole list on every booking status change — ~2,163 rebuilds per
721-booking run, **about 12.7 minutes of frozen window**. Now plain items
updated in place. The per-row "x" was redundant ("Remove selected" exists).

### The GUI hang — a `print()` on the UI thread

`py-spy dump` found it in ten seconds: the main thread blocked inside
`print("GUI: _on_login_check entered")`, 0% CPU, no children. The GUI starts
from a `.bat`, so it owns a console, and **Windows QuickEdit pauses console
output on any click** — blocking the writer. All 8 GUI prints are logger
calls now, guarded by an AST test.

### structure_watch — 61 seconds per session, never worked

`aria_snapshot()` inherited the 30-second action timeout; both watched
selectors timed out on **every session since it was wired up** (09-23, 09-28,
09-30) and those baselines have never been captured. Now a 4s budget, and a
timeout logs at info rather than error.

### Watchdog

Per-run counter reset (a 5-day-old process was reporting 27% nav-retries
against an actual 0%), hung-window detection with automatic `py-spy` dump,
single-instance lock, and **notifications OFF by default** — they were firing
because closing the GUI looked like a crash. A clean shutdown
(`gui.shutdown_complete` / `single_instance.released`) is now silent.

### Data collection

`final_payment_date` + `net_balance_due` (ESPRESSO) and `region` (NCL) were
being parsed and discarded. Now stored. **Deliberately still NULL:**
ESPRESSO's `nights`/`guests_count` — re-checked against 6 captures,
`occupancy` is ambiguous, `totalGuests` reads "(Pending)", `duration` is 0.
A NULL costs signal; a fabricated value teaches something false.

## OPEN — READ BEFORE TOUCHING ESPRESSO

**The account could not hold a session on 2026-09-30.** Every login died
within 60–95 seconds; **0 of 723 bookings completed all day**, across two
runs. Even `navigate_home` landed on `/login`. The loop guard correctly
stopped rather than hammering (`reason: too_soon`).

It ran fine for hours on the 29th with no code change to the session path, so
the cause looks external: either the account is active **somewhere else**
(one session per account — check for a CruisingPower tab in a normal browser,
another machine, a phone), or the portal is throttling after repeated logins
(4 submitted that day).

**Diagnose before coding:** leave it 20–30 minutes, close any other
CruisingPower tab, log in once by hand, and watch whether the session
survives two minutes with the scanner NOT running. That single observation
separates "something else holds the account" from "we are being throttled".

Also open:
- Right-click force-rescan / un-exclude in the GUI (backends exist and are
  tested; no context menu yet).
- Perk-loss rules — **mostly closed 2026-09-30**, see
  [ESPRESSO_PERK_TIERS.md](ESPRESSO_PERK_TIERS.md). Four mutually exclusive
  perk tiers (ALL INC 2PK / RETREAT / NOPERK / STANDARD); all 148 recorded
  tier changes are downgrades, and every one is now named on the result.
  A positive CRUISE_PROMO is the PRICE of a perk and stays subtracted — the
  "it's a surcharge, don't subtract it" fix is a **documented dead end**.
  Still open: the scanner does not read the Promotions/Compare screen, so it
  reports *that* a perk is given up, never what keeping it would cost.
- MSC discount functions built and tested but **not wired**.
- `structure_watch` root cause — now cheap, but still never captures.

## METHOD

Every fix here came from **measuring the log or the database**, not from
reading code and guessing. **Comments in this codebase have lied six times** —
"runs for every branch above", "the rest of the batch continues", "keeps its
ERROR row" — each describing an intention the code contradicted, each hiding a
real bug for months.

Two test anti-patterns bit repeatedly today: **matching prose instead of
code** (strip comments and docstrings via AST), and **character-distance
windows** (`assert X in src[i:i+400]` — assert structure instead).

And: **a status code is evidence; a URL that failed to change is not.** One
test reported headless as SUPPORTED because a 404 error page served at the
requested URL satisfied a "did we get bounced?" check.
